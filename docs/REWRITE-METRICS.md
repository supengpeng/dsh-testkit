# dsh-testkit 重构量化标准

> **状态**：随 [RFC 0001](rfc/0001-rust-core-full-rewrite.md) 裁决。配套：[REWRITE-DESIGN.md](REWRITE-DESIGN.md)。
>
> **本文件的总原则只有一条**：**凡不能被机器测量的指标，不得出现在门槛里。**
> 原稿的 50 条指标里有 6 条违反了这条（列在 §1），它们已被逐条裁定——改写或删除，不留"人工审计"藏身。

---

## 0. 总原则与判定规则

### 0.1 四条原则

1. **所有指标必须可自动测量**。任何"人工审计""抽样复核""大致""基本"都不是指标，是意见。
2. **门槛（Gate）不过即阻断**；**目标（Target）不过仅告警**。
3. **每条指标都必须绑定一个能复跑的命令**，并且必须有一条**负向证明**（证明这个守卫会红，而不是安慰剂）。这是本仓既有的纪律（[rfc/README.md](rfc/README.md) §6）。
4. **测量工具本身也要被测**（§16）。

### 0.2 判定规则

| 情况 | `overall` |
|---|---|
| 任一指标 `value` 未达 `gate` | `fail`（`blockers` 非空） |
| 全部达 `gate`，有指标未达 `target` | `warn`（`warnings` 非空） |
| 全部达 `target` | `pass` |

### 0.3 两类指标

| 类别 | 有效期 | 说明 |
|---|---|---|
| **重构期指标** | 阶段 0–3 | 对拍一致性（A）、spec 覆盖率（B）、部分确定性（C）——阶段 3 之后失去意义 |
| **常态指标** | 永久 | 性能（D）、防篡改（E）、组合（F、L）、能力版本（G）、协议（H）、安全（I）、工程（J）、分层（K） |

> 原稿没有区分这两类，导致"对拍通过率"被当成永久门槛——而阶段 3 删掉旧实现之后，**没有任何东西可对拍**。

## 2. A. 对拍一致性（重构期）

> 只对**确定性的**部分设门槛。非确定性字段按 [REWRITE-DESIGN.md](REWRITE-DESIGN.md) §9.3 的等价关系表归一化后再比。

| 编号 | 指标与定义 | 门槛 | 目标 | 测量 |
|---|---|---|---|---|
| A1 | **对拍通过率** = 通过的对拍用例数 / 总对拍用例数 | **100%** | 100% | 对拍器（`reconcile` 子命令）自动统计 |
| A2 | **对拍字段覆盖完整度** = 对拍器实际比对字段数 / spec 声明的字段数 | **100%** | 100% | 对拍器自检：比对字段清单 vs spec schema |
| A3 | **对拍字段覆盖率** = spec 声明的字段数 / `run.json` schema 的叶子字段数 | **100%** | 100% | 枚举 [run-report.schema.json](../schemas/run-report.schema.json) 的叶子路径，与 spec 声明集合作差 |
| A4 | **差异分类可复现率** = 同一份差异输入两次分类结果相同的比例；辅助：`unknown` 分类占比 | **≥ 99%** / `unknown` = 0 | 100% / 0 | 对同一批差异跑两次分类器，比对输出 |
| A5 | **归一化规则正确率** = 注入的已知差异被检出且归因正确的比例 | **≥ 99%** | 100% | 反向测试：注入差异 → 验证未被归一化掩盖 |
| A6 | **对拍器自身覆盖率**（行 / 分支） | 行 ≥ 90% / 分支 ≥ 85% | 行 ≥ 95% / 分支 ≥ 90% | `cargo llvm-cov` |

**三条展开说明**：

- **A1 的 100% 是硬门槛，但它是可谈判的——谈判的地方在 [RFC 0001](rfc/0001-rust-core-full-rewrite.md) §7 停止线 2**（连续 4 周 < 95% 且差异集中在非确定性字段 ⇒ 判定"旧行为不可冻结"并退出本方向）。门槛本身不放松，放松门槛的方式是**取消这个方向**，而不是把 100% 改成 95%——那会让"新 = 旧"这个目标变成一句空话。
- **A3 为什么能提到 100%**：`run.json` 的字段集由 schema 完全枚举（`additionalProperties: false`），spec 的字段集由 spec schema 枚举。两个有限集合求差是纯机械动作，没有"审计"的余地。**任何 A3 < 100% 的情况都意味着有一类输出没有被对拍覆盖**——那是必须补的，不是可以接受的。
  - **2026-10-11 勘误（阶段 0 实测）**：`run.json` schema **并非完全枚举**——有 **4 个开放子树**未锁 `additionalProperties`：`cases[].steps[].assertions[].assertion`（`schemas/run-report.schema.json:238-286`，节点注释明写"不锁死"）、`cases[].steps[].notes`、`cases[].notes`、`policySnapshot.sandbox`。分母不封闭时"A3 = 100%"可被"开放子树里新增字段"悄悄满足。故 A3 增加一条配套纪律：**开放子树必须显式列出，且落在子树内而未被声明的叶子一律进 `uncompared_fields`**——"没比"始终可见（与设计 §9.3 纪律 1 同源）。当前实测读数：叶子 77 / 已声明 54 / 未声明 23，**A3 = 70.13%**（清单见 `spec/contracts/reconcile-fields.yaml` 的 `undeclared_paths`）。
- **A4 的 `unknown` 必须为 0**：分类器允许**五类**归因（`product_bug` / `case_bug` / `driver_bug` / `env` / `flaky`，沿用既有 `src/runtime/runlog.ts:17` 的枚举）。"分不出来"不是一个类别，是一条缺陷。
  - **2026-10-11 勘误（阶段 0 实测）**：原文写"四类"且漏了 `driver_bug`。实测真源三处一致为 **5**：`src/runtime/runlog.ts:17` 的枚举、`schemas/run-report.schema.json:148`、`src/analysis/classify.ts:130-136` 的 `FAILURE_CATEGORY_LABEL`（并有测试 `tests/report-standard.test.mjs::FAILURE_CATEGORY_LABEL：5 类枚举齐全且非空` 守着）。
  - **`unknown` 为 0 是结构保证，不是约定**：`classify.ts` 的返回类型是 `FailureCategory | undefined`（`unknown` 不在类型里），判定表互斥且穷尽（`errored` 兜底 `driver_bug`、`failed` 兜底 `product_bug`），`undefined` 只用于 passed / skipped——那是"没有失败可归因"，不是"归因不出来"。
  - 另注：判定表**头注写 11 条**路径，实现是 **10 个 return 点**——"预算超限"并入 `ENV_PATTERNS` 而不新增第 6 类，理由在该文件头 `:20-31`。

## 3. B. Spec 覆盖率（重构期）

| 编号 | 指标与定义 | 门槛 | 目标 | 测量 |
|---|---|---|---|---|
| B1 | **旧代码分支覆盖率** = spec 覆盖的旧 TS 代码分支数 / 旧代码总分支数 | **≥ 90%** | ≥ 95% | **V8 / c8 覆盖率**（Node 侧），不是 `cargo-llvm-cov` |
| B2 | **能力覆盖** = spec 覆盖的能力数 / `HostCapability` 联合类型的能力总数 | **100%** | 100% | 从 `src/cases/types.ts` 枚举 `HostCapability`，与 spec 关联 |
| B3 | **版本覆盖** = spec 覆盖的 DSH 版本数 / 声明的支持版本总数 | **100%** | 100% | 版本清单与 spec 关联 |
| B4 | **环境覆盖** = spec 覆盖的环境组合数 / 声明的环境组合总数 | **100%** | 100% | 环境矩阵与 spec 关联 |
| B5 | **审批路径覆盖** = spec 覆盖的交互/审批路径数 / 声明的路径总数 | **100%** | 100% | 路径清单（`interaction` driver 的分支）与 spec 关联 |

**B1 的工具选择说明**：原稿用 `cargo-llvm-cov` 测"旧代码分支覆盖率"。旧代码是 TypeScript，`cargo-llvm-cov` 测不到它——这是一处**纯工具错配**。正确做法是 Node 侧覆盖率（V8 内建或 c8）。Rust 侧覆盖率是**另一个指标**（J1），两者不能混用同一个数字。

**B2 为什么能 100%**：`HostCapability` 是一个有限联合类型（**20** 个成员，见 `src/cases/types.ts:26-50`），可机械枚举。与之对照，B1 的分支数无法先验枚举，所以 B1 才是 ≥90% 而不是 100%。

> **2026-10-11 勘误（阶段 0 实测）**：原文写"19 个成员"。实测为 **20** 个（`spec/contracts/capabilities.yaml` 有逐个成员与探测来源）。原数字会让一个能力永远不进分母，B2 就成了伪 100%。另注：20 个里**只有 16 个有关联行为**，4 个（`agentLoop` / `storage` / `timer` / `client`）在 `src/` 里零消费点——按 `spec/README.md` §6「禁止为凑覆盖率写空条目」，这 4 个必须各有一条**显式 `declared-only`** 条目，或在阶段 1 从联合类型删掉并同步 `src/host-facade.ts` 与 `SCENARIO-SPEC.md`。

## 4. C. 确定性 / Flaky

| 编号 | 指标与定义 | 门槛 | 目标 | 测量 |
|---|---|---|---|---|
| C1 | **同种子复现率** = 相同种子下产生相同结果的运行次数 / 总运行次数 | **100%** | 100% | 固定种子跑 10 次，逐字段比对 |
| C2a | **Flaky 布尔判定**（N=5）：存在任一不一致即必须归因 | **未经归因的不一致 = 0** | 0 | 每用例跑 5 次；不一致必须落到 `failureCategory` |
| C2b | **Flaky 率**（N ≥ 50，周期性） | **≤ 1%** | 0 | 周期性跑 N ≥ 50 次；见下方分辨率说明 |
| C3 | **非确定性字段清单完整度** = 已声明的非确定性字段数 / 实测的非确定性字段数 | **100%** | 100% | 跨环境重复跑，比对差异字段集 |
| C4 | **归一化后确定性** = 归一化后相同输入产生相同输出的比例 | **100%** | 100% | 同种子跑 10 次 |

### C2 的统计分辨率（修正原稿的硬伤）

原稿写"门槛 ≤ 0.1%，测量：每用例跑 5 次"。这**在统计上不可能**：5 次运行若出现 1 次不一致，观测到的比例是 20%；若 5 次全一致，只能说"该用例的 flaky 率 < 20%"。

正确的做法是把**分辨率写进指标**：

> N 次运行能给出的 flaky 率**分辨率上界是 1/N**。
> - N = 5 ⇒ 只能回答"是否稳定"，不能回答"比例是多少" → 所以 C2a 用**布尔**判定。
> - 想守 ≤ 1%，需要 **N ≥ 50**（且必须在多次运行间不重排用例顺序）→ 这就是 C2b。
> - 想守 ≤ 0.1%，需要 **N ≥ 1000**——对真实宿主场景不现实，所以**门槛定在 1%，不假装能守 0.1%**。

> 原稿的 0.1% 若照抄，实际效果是"这条指标永远显示 pass（因为 5 次样本量根本测不出），但没有任何保护力"——**一个永远绿的指标比没有指标更危险**。

### C1 vs C4 的区别

- **C1** 问"同样的种子 ⇒ 同样的结果吗"（种子可控性）。
- **C4** 问"归一化之后 ⇒ 还是同样的结果吗"（归一化规则的完备性）。
后者若失败，说明归一化**过度**了（掩盖了真实差异），这与 A5 是一对反向约束。

## 5. D. 性能（常态，基线冻结）

| 编号 | 指标与定义 | 门槛 | 目标 | 测量 |
|---|---|---|---|---|
| D1 | **单用例执行时间比** = 当前基线值 / **冻结基线值** | **≤ 1.10** | ≤ 1.00 | `criterion` 基准 + 固定容器 |
| D2 | **全套执行时间比** = 同上 | **≤ 1.15** | ≤ 1.00 | 固定环境跑全量场景 |
| D3 | **内存峰值比** = 同上 | **≤ 1.20** | ≤ 1.00 | `dhat` 或进程级 RSS 采样 |
| **D4a** | **签名次数上界** = 实际签名次数 ≤ `ceil(结果记录数 / B) + 2`（B = 批大小，默认 4096） | **必须成立** | 计数器比对，**与机器速度无关** |
| **D4b** | **单次签名耗时**（基线观测值，**不是门槛**） | 无门槛 | `criterion`；与 D1–D3 同一套冻结基线 + 环境指纹机制，指纹不匹配时只记录不阻断 |
| D5 | **RPC 往返延迟** = 单条 JSON-RPC 请求的 P99 | **≤ 5ms** | ≤ 2ms | 协议层埋点（`src/trace` 已有 spans 机制） |

### D1–D3 的基线冻结（修正原稿的致命缺陷）

原稿把这 D1/D2 的分母定义为**旧实现**。但 [RFC 0001](rfc/0001-rust-core-full-rewrite.md) 决定 4 的**终点就是删除旧实现**。基线一旦随旧代码消失，这三条指标在阶段 3 之后无法计算。

修正：**基线在阶段 0 实测后冻结成数值**，落进既有 `baseline/` 目录：

```text
baseline/
  README.md          # 既有：记录基线读数
  perf-baseline.json # 新增：冻结的 D1/D2/D3 分母
  env.json           # 新增：基线采集时的环境指纹（平台/CPU/Node/容器镜像）
```

**三条纪律**：

1. 只有 `env.json` **完全匹配**时才比较数值；环境变了必须重采基线并标注（否则"回归"其实是换机器了）。
2. 基线重采必须**由人发起并记录原因**（不允许 CI 自动重采——那等于自动抹平回归）。
3. 阶段 3 删旧实现**之前**必须完成基线冻结；冻结缺失则 D1–D3 自动降级为"仅记录，不阻断"，并在报告里标 `degraded`。

### D4a / D4b：为什么不再是"待实测"

原稿写"Ed25519 签名约 50μs / 验证约 150μs"并据此设门槛 ≤5%。这些数字**没有出处**；但更根本的问题是：**"耗时占比"本身就是个机器相关的量**——不可移植、也无法先验设定。

解法在 [REWRITE-DESIGN.md](REWRITE-DESIGN.md) §7.3.1（[RFC 0001](rfc/0001-rust-core-full-rewrite.md) §8 Q4）：**改设计，而不是调门槛**。批量 Merkle 签名让开销与消息数解耦——数万条结果按 B=4096 只产生个位数签名，于是"占比 ≤ 5%"这个门槛**不再必要**：它要防的瓶颈已经不存在了。

| 编号 | 指标 | 门槛 | 测量 |
|---|---|---|---|
| **D4a** | **签名次数上界** | `签名次数 ≤ ceil(结果记录数 / B) + 2` **必须成立** | 计数器比对（**结构量，与机器无关**） |
| **D4b** | **单次签名耗时** | **无门槛**（基线观测值） | `criterion`，与 D1–D3 同一套冻结基线 + 环境指纹 |

> **两条方法学纪律**：
> ① 门槛是**结论**，不是**前提**。先实测、后定门槛；先定门槛、再让实测去凑，是自欺。
> ② **比"定一个能过的门槛"更好的做法，是让它不成为瓶颈**：凡需要"跑一次看看"的门槛，先问能不能换成可计数的结构量——D4a 就是这么来的。
## 6. E. 防篡改（常态）

> 设计见 [REWRITE-DESIGN.md](REWRITE-DESIGN.md) §7。原稿的 E4「**外部**锚定成功率」已按 RFC Q2 的裁决（2026-10-10）**改写**为「**本地**锚定写入成功率」——外部锚定本期不实现，而本地锚定离线可测，于是它从"一条永远达不到的门槛"变成真门槛。

| 编号 | 指标与定义 | 门槛 | 目标 | 测量 |
|---|---|---|---|---|
| E1 | **签名验证通过率** = 签名验证通过的记录数 / 总记录数 | **100%** | 100% | TS 侧零依赖验证器 |
| E2 | **篡改检出率** = 注入篡改后被检出的比例（5 类：改字段 / 删记录 / 重排 / 插入 / 改签名，每类 ≥ 10 个用例） | **100%** | 100% | 注入测试 |
| E3 | **链完整性** = 链头哈希与全链重算一致的运行比例 | **100%** | 100% | TS 侧独立验证器 |
| E4 | **本地锚定写入成功率** = 链头成功写入本地锚定目录的运行数 / 总运行数 | **≥ 99%** | 100% | 写入后**回读校验**；写不进必须如实标记，**不得静默降级** |
| E5 | **独立验证器零依赖** = 运行时依赖数（不含 Node 内置） | **= 0** | 0 | `npm ls --prod` 检查 |

**E2 的边界必须写在报告里**：本机制对**重写整链**检不出（[REWRITE-DESIGN.md](REWRITE-DESIGN.md) §7.5）。因此 E2 的结论不得表述为"报告不可篡改"，只能表述为"报告中的篡改可被验证者发现"。**任何超出这个边界的表述都是过度承诺**，包括在 README 与发布说明里。

## 7. F. 组合正确性（常态）

| 编号 | 指标与定义 | 门槛 | 目标 | 测量 |
|---|---|---|---|---|

1. `--remap-path-prefix` 抹掉构建路径；
2. 固定 `SOURCE_DATE_EPOCH`；

## 13. L. 组合覆盖率（新增）

> **原稿缺这一类**，而 [RFC 0001](rfc/0001-rust-core-full-rewrite.md) 决定 5 的理由正是"组合覆盖必须可度量"。F 类只测"冲突能否被检出"，不测"组合覆盖到了第几层"——那是两件事。

| 编号 | 指标与定义 | 门槛 | 目标 | 测量 |
|---|---|---|---|---|
| L1 | **Pairwise 覆盖率** = 已覆盖的插件/参数对 / 依赖图剪枝后的必要对总数 | **≥ 90%** | 100% | 从 `cases/` 与 plan 提取参数对，与剪枝后的必要集合作差 |
| L2 | **3-wise 覆盖率**（仅对有依赖关系者） | **≥ 70%** | ≥ 85% | 同上，三维组合 |
| L3 | **子图剪枝正确性** = 被剪掉的子图"确实不受影响"的验证通过率 | **100%** | 100% | 对每条剪枝决策，用未剪版本复跑并比对结果 |

**L3 是 L1/L2 的前提**：剪枝错了，覆盖率再高也是覆盖了错的集合。所以 L3 必须能独立复跑，且它对每条剪枝决策都要有"不剪会怎样"的对照。

**组合空间为什么必然要剪枝**：N 个插件有 O(2^N) 种组合、激活顺序有 N! 种。全测不可能。剪枝规则基于**依赖图**（只测有依赖关系的对），并在报告里标出"被剪掉的是什么、依据是什么"——**剪枝必须可见**，否则"覆盖率达标的报告"会掩盖一个未被测的子集。

## 16. 报告格式

每次 CI 运行输出：

```json
{
  "run_id": "uuid-v7",
  "timestamp": "<TS>",
  "stage": "phase-2",
  "overall": "pass | warn | fail",
  "metrics": {
    "A1": { "value": 1.0,  "gate": 1.0,   "target": 1.0,  "status": "pass" },
    "A3": { "value": 1.0,  "gate": 1.0,   "target": 1.0,  "status": "pass" },
    "C2b": { "value": 0.0, "gate": 0.01,  "target": 0.0,  "status": "pass", "n": 50 },
    "D4a": { "value": 3, "gate": 5, "target": 5, "status": "pass" },
    "J5": { "value": null, "gate": 1.0,   "target": 1.0,  "status": "pending", "blocked_by": "reproducible-build-config" }
  },
  "by_layer": {
    "L0": { "count": 0,  "confidence": "static" },
    "L1": { "count": 12, "confidence": "simulated" },
    "L2": { "count": 30, "confidence": "simulated" },
    "L3": { "count": 45, "confidence": "real" },
    "L4": { "count": 8,  "confidence": "real" },
    "L5": { "count": 5,  "confidence": "real" },
    "L6": { "count": 3,  "confidence": "real" }
  },
  "uncompared_fields": [],
  "blockers": [],
  "warnings": ["C2b 未达目标值"],
  "signature": "ed25519:...",
  "chain_head": "sha256:..."
}
```

**三个字段值得单独说明**：

- **`status: "pending"`** 是本版新增的第三个状态（原稿只有 pass/warn/fail）。它表达"门槛尚未确定或前置未完成"，**既不阻断也不放行**。没有这个状态，J5（可复现构建）这类"前置未完成"的指标只能被迫二选一：要么用一个假门槛，要么默认通过——两者都是欺骗。
- **`uncompared_fields`** 必须出现在报告里（[REWRITE-DESIGN.md](REWRITE-DESIGN.md) §9.3 的纪律 1）：**"没比什么"和"比了什么"同等重要**。
- **`by_layer` 不允许混合聚合**：这是 K3 的落地形式。

## 17. 未达标处理

| 未达标类型 | 处理 |
|---|---|
| A / B / C / E / F / G / H / I / K / L 类 | **阻断**，必须修复 |
| D 类（性能） | D1 / D2 阻断；**D4a 阻断**；D3 / D5 告警；D4b 只记录（无门槛）。`pending` 状态保留给 J5（可复现构建配置完成前） |
| J 类（工程质量） | J1 / J2 阻断；J3 / J4 告警；J5 在配置完成前为 `pending` |
| 阶段退出条件 | 任一未达即阻断进入下一阶段 |

**任何例外必须**：

1. 书面记录原因（写进 `exceptions.md`）；
2. 明确修复计划与时间点；
3. 经至少两人评审；
4. ——**并且必须写明这条例外在哪个阶段失效**（无期限的例外就是取消的门槛）。

> 原稿的第 4 条只写了"记录到 `exceptions.md`"，没有失效期。一条没有失效期的例外，效果等同于把门槛删掉而保留它的名字。

## 18. 指标自身验证

每个指标的测量工具必须：

- 有单元测试；
- 有**已知输入下的预期输出**（含边界）；
- 在 CI 中**定期自检**；
- 有**负向证明**（故意造出该缺陷，工具必须红）。

测量工具的错误率门槛：

| 工具 | 错误率门槛 |
|---|---|
| 对拍器 | ≤ 0.1% |
| 覆盖率工具 | ≤ 0.1% |
| 性能基准 | ≤ 1% |
| 签名验证器 | **0%** |
| 分层校验器 | **0%** |

**对拍器与覆盖率工具为什么允许非零**：它们有测量噪声（覆盖率受编译选项影响、对拍受环境影响）；而签名验证器与分层校验器是**纯函数判定**，没有任何允许出错的理由——它们的错误率只能是 0。

### 原稿 19 条缺点的处置

| 原稿缺点 | 处置 |
|---|---|
| 1 双语言栈维护成本 | **保留**，进 RFC §5「成本」与 §4 方案 C 的代价栏 |
| 2 规格提取成本被低估 | **保留并强化**，成为 RFC §7 停止线 1 |
| 3 确定性无法 100% 保证 | **保留并落地**为 [REWRITE-DESIGN.md](REWRITE-DESIGN.md) §6.4（含 `HashMap` 硬纪律） |
| 4 哈希链无法阻止整链重写 | **保留并写入边界**：[REWRITE-DESIGN.md](REWRITE-DESIGN.md) §7.5 + 本文件 E2 说明 |
| 5 每消息签名开销 | **保留并处置**：只签结果消息（[REWRITE-DESIGN.md](REWRITE-DESIGN.md) §7.1） |
| 6 四层防御认知负担 | **保留并补设计**（[REWRITE-DESIGN.md](REWRITE-DESIGN.md) §5.3），`unsafe` 入口降为 `Static` |
| 7 多插件组合空间爆炸 | **保留并量化**：新增 L 类指标 |
| 8 通用化稀释 strict 专注度 | **已消解**：三档 preset 把"冻结"与"发布"分开 |
| 9 TS 验证器信任问题 | **保留**，进 [REWRITE-DESIGN.md](REWRITE-DESIGN.md) §7.4（零依赖验证器） |
| 10 Rust 编译时间 | **保留**，进 RFC §5 成本；缓解手段（`sccache` / `lld`）列入实现建议 |
| 11 对拍器无法自证 | **保留并处置**：新增 A4/A5/A6 + 反向测试纪律 |
| 12 完全重构时机风险 | **保留**，成为 RFC §7 停止线 2 |
| 13 可信度分级无法阻止误用 | **保留并处置**：`release` 档禁用绕过入口（[REWRITE-DESIGN.md](REWRITE-DESIGN.md) §8.4 硬约束 6） |
| 14 没解决"测什么" | **保留**：场景模板库 + 覆盖矩阵已存在（`pnpm run verify:cases`、`insight coverage`），本版补 L 类覆盖指标 |
| 15 第三方宿主适配成本 | **保留**，进 RFC §8 待决事项（本仓当前只适配 DSH，未扩张） |
| 16 确定性调度限制并发 | **已解决**：[REWRITE-DESIGN.md](REWRITE-DESIGN.md) §6.3 的"用例间多进程 / 用例内单线程"模型 |

| 18 Rust 测试生态不成熟 | **已证伪**：RFC §4 的下载量事实（`insta` 1.09 亿 / `criterion` 3.03 亿 / `loom` 7070 万） |
| 19 分层模型可能被误用 | **保留并处置**：本文件 K2/K4 双指标 + `release` 档硬约束 |
