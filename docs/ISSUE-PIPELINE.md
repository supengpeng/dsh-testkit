# issue 提炼流程（Issue → Scenario Pipeline）

> 这是**我们的作业手册**：你给我 issue，我按本流程把它变成可复现的场景数据，
> 再把数据变成插件能力。每一次迭代都走同一条流水线。

---

## 0. 提炼闸门：要不要提炼，由人决定（先读这一节）

提炼的默认状态是**不动**。一次提炼 = 一个**批次**，它在机制上被三处闸门夹住：

| 闸门 | 谁发起 | 机制 | 违反时 |
|---|---|---|---|
| ① 开启本轮 | **人** | `/testkit issue open <范围说明>` | 模型调 `testkit_propose` 直接报「本轮提炼未开启」 |
| ② 提交提案 | 模型 | `testkit_propose` 只写 `pipeline/proposals/` | 永不写 `cases/`；质量预检不过**不落盘** |
| ③ 落地结案 | **人** | `/testkit issue approve` / `/testkit issue reject` | 未结案前**不允许**开启下一批 |

规矩三条：

1. **一次一批**：同一时间只允许一个 open 批次。上一批没结案就开不了下一批——
   这就是「本次提炼完成、用户同意之后才能进行下次提炼」的机制化表达。
   模型无法自己开启批次，也没有批准权：**批准能力只挂在人类命令面**。
2. **质量前置**：提案在**落盘之前**就要过质量红线（§6 的机器判据），不合格直接打回，
   `proposals/` 里不留半成品。这是"高效"的来源——读不到垃圾，
   也就不会出现「看起来在测、其实没测」的假象。
3. **落地留痕**：批准会分配正式 `TK-XXXX`、写 `cases/`、重建索引；
   拒绝只改台账，提案文件留在 `proposals/` 里留痕。
   台账是唯一真源：`pipeline/ledger.json`。

常用命令：

```
/testkit issue                                看台账与当前批次
/testkit issue open dsh-memory 发包面 2 条      开启本轮
/testkit issue show P-0001                    看提案正文与预检明细
/testkit issue approve --all                  批准落地（分配 TK 号 + 重建索引）
/testkit issue reject P-0002 判据不成立         拒绝（留痕）
/testkit issue close 本轮不提炼了               作废本批
```

> 模型侧的闸门面只有两个：`testkit_propose`（提交提案）与只读的 `testkit_pipeline`（看台账）。
> 它们**拿不到** `approve`——那是刻意的。

**闸门的边界（诚实说明）**：它约束的是 **dsh-testkit 自己的提炼通道**——
模型拿不到 `approve`，`testkit_propose` 也永远不写 `cases/`。
但如果模型手里有通用的文件写入工具，它当然可以直接改仓库文件；
闸门挡的是"顺手批量提炼"，不是"恶意越权"。真要强隔离，只能靠宿主的权限沙箱。

**落地之后**：提案自带的 `status` 会**原样保留**（多数是 `draft`，不进默认回归集）。
先 `/testkit run TK-xxxx` 验收，通过后再决定是否改成 `active` 收进回归网。

## 1. 流水线总览

```
人：/testkit issue open <范围>        ← ① 决定"要不要提炼"
   │
   ├─ S1 还原事实 ────────── 症状 / 期望 / 触发条件 / 环境
   ├─ S2 定位干预点 ──────── 归类到一个 kind（决策树见 §4）
   ├─ S3 最小化条件 ──────── 把偶发条件收窄成确定性最小子集
   ├─ S4 写 case ────────── 提案正文（id 占位 TK-0000 + 断言）
   ├─ S5 判定可行性 ──────── 现有 driver 够不够？
   │        ├─ 够 ──▶ 直接跑，出结果
   │        └─ 不够 ─▶ 补 driver，再跑
   ▼
模型：testkit_propose                ← ② 只落 pipeline/proposals/（预检不过不落盘）
   ▼
人：/testkit issue approve / reject   ← ③ 决定"是否落地"，并结案本批
   ▼
cases/TK-XXXX.yaml + index.yaml 更新 + runs/<RUN-ID>/ 报告 + 汇报
```

**关键纪律**：S3 不做好，后面全是白工。issue 里的"偶发"必须被还原成"必然"。

**第二条纪律**：S4 的产物是**提案**，不是场景。判据没写完（还有 `TODO`）就提交，
会被质量预检直接挡回——不要指望"先落盘、回头再补"。

## 2. 输入形态

issue 可以是以下任意形态，我都能接：

| 形态 | 例子 | 我要做的补充 |
|---|---|---|
| 链接 | GitHub issue URL | 抓取正文 + 评论（复现步骤常在评论里） |
| 粘贴文本 | 报错栈 + 描述 | 直接用作 S1 输入 |
| 一句话 | "工具结果太长就崩" | 需要向你追问环境与期望（见 §7） |
| 日志/会话导出 | 一段 DSH 会话 JSON | 从事件序列反推触发路径 |

## 3. 五个步骤的细则

### S1 还原事实

从 issue 里抽出四件事，缺一问一：

| 项 | 说明 |
|---|---|
| **症状** | 实际发生了什么（报错原文、界面表现、日志行） |
| **期望** | 应该发生什么（issue 作者认为的正确行为） |
| **触发条件** | 什么操作序列能撞上；包含的环境前提（版本、平台、配置、并发度） |
| **可判定性** | 症状能不能被自动断言？不能的话，退化成什么可观测的代理指标？ |

> 报错原文**照抄不翻译**，直接进 `source.summary`。

### S2 定位干预点

用 §4 的决策树把它归到**一个** kind。归错会让 driver 选错，表现为"case 写得别扭"。

判据：**这个 issue 的触发条件，在 DSH 里是由哪个扩展点制造的？**
例：
- "模型返回了畸形 JSON" → 条件由模型产出决定 → `llm`
- "工具结果太大会崩" → 条件由工具返回值决定 → `tool`
- "用户不回答提问就卡住" → 条件由人的行为决定 → `interaction`

### S3 最小化条件

把 issue 的场景收敛成**确定性最小子集**：

| 动作 | 说明 |
|---|---|
| 去掉无关变量 | 只保留触发问题必需的那一个 |
| 把随机变确定 | "有时候" → 指定触发第 N 次；"偶尔超时" → 固定延迟 |
| 把外部依赖替换 | 真实联网 → 假 provider；真实模型 → 固定流 |
| 标定边界 | "太长" → 明确指出刚好越界的那个长度 |
| 固定环境 | 在 `runtime.requires` 里显式声明依赖的宿主能力 |

**产出**：一段能写进 `setup` 的确定性描述，以及一组"刚好越界"的边界值。

### S4 写 case

按 [SCENARIO-SPEC.md](SCENARIO-SPEC.md) 写 `cases/TK-XXXX.yaml`。

写断言时的三条要求：

1. **断言可观测事实**，不断言实现细节（除非 issue 就是在说实现细节）
2. **先写"应该成功"的对照断言**，再写"问题被正确处理"的断言 —— 否则无法区分"修好了"和"根本没跑到"
3. **标定边界两侧**：越界前 + 越界后各一条，避免"改了阈值也算通过"

### S5 判定可行性

对照 `src/kinds/` 现状：

| 结论 | 动作 |
|---|---|
| 现有 driver 直接支持 | 跑 |
| 需要给 driver 加参数 | 扩 driver + 更新 SCENARIO-SPEC |
| 需要新 kind | 新 driver + 注册 + 更新 ARCHITECTURE §7 与 SCENARIO-SPEC §3 |
| 当前能力测不了 | 标 `status: blocked`，在汇报里说明缺口与方案 |

## 4. 归类决策树

```
issue 说的是"模型看到/发出了什么"？
   ├─ 输出内容/流式/重试/用量   → llm
   └─ 提示词/上下文/变量         → prompt
issue 说的是"某个工具的行为"？        → tool
issue 说的是"人要回答/批准什么"？      → interaction
issue 说的是"会话/命令/目标的状态"？   → session
issue 说的是"文件/进程/网络"？         → resource
issue 说的是"端到端结果不对"？         → agent
issue 说的是"界面上看到什么"？         → ui
说不清                                → 先 agent（黑盒），跑通后再下沉到具体 kind
```

**下沉原则**：能端到端复现但说不清归类的，先写 `agent` 黑盒 case 锁住行为；
等根因清楚了，再补一条下沉的精确 case（黑盒那条保留当回归网）。

## 5. 每批迭代的交付物

处理一批 issue 后，交付：

| # | 产物 | 位置 |
|---|---|---|
| 1 | 提案（提交时） | `pipeline/proposals/<BATCH-ID>/` |
| 2 | 批次台账与裁决留痕 | `pipeline/ledger.json` |
| 3 | 新增/修改的场景数据（批准后） | `cases/TK-*.yaml` |
| 4 | 索引与溯源更新（approve 自动重建） | `cases/index.yaml` |
| 5 | 新增/扩展的 driver（如有） | `src/kinds/*.ts` |
| 6 | 运行报告 | `runs/<RUN-ID>/report.md` |
| 7 | 能力缺口清单（测不了的） | 汇报正文 |
| 8 | 规范文档更新（如引入新字段/新 kind） | `docs/SCENARIO-SPEC.md` |

> 台账（`pipeline/ledger.json`）是**要不要提炼 / 有没有落地**的唯一证据：
> 它记着谁在什么时候开了哪一批、每条提案被批准还是拒绝、落地成了哪个 `TK-` 号。

## 6. case 质量红线

一条 case 不满足以下任一条，**不允许合并进 `cases/`**：

- [ ] **可复现**：连续跑 N 次结果一致（`repeat: 3` 验证）
- [ ] **可断言**：有至少一条机器可判定的断言
- [ ] **可回滚**：不留下污染宿主状态的残留（跑完再跑一次别的 case 不受影响）
- [ ] **可溯源**：`source.issue` 非空
- [ ] **有对照**：包含"该成功的地方成功了"的断言
- [ ] **无外网依赖**：不真的访问互联网（除非 `requires` 里显式声明并允许 skip）

### 机器强制到哪一步（落实在提炼闸门里）

| 红线 | 机器强制？ | 拦在哪 |
|---|---|---|
| 可溯源（`source.issue` 非空） | ✅ 阻断 | `testkit_propose` 落盘前 ＋ approve 落地前 |
| 可断言（至少一条 `expect`） | ✅ 阻断 | 同上 |
| 没有 `TODO` 残留 | ✅ 阻断 | 同上 |
| `id` 必须是占位 `TK-0000` | ✅ 阻断 | 同上 |
| schema 合法（kind / 断言词 / 字段） | ✅ 阻断 | 同上 |
| 有对照（至少一条正向断言） | ⚠️ 只提醒 | 机器判不准，交给人裁决 |
| 可复现 / 可回滚 / 无外网 | ❌ 机器不判 | 靠 §3 S3 与人工审查 |

**为什么只把机器真能判定的写成阻断**：把判不准的写成阻断，只会逼人绕过闸门；
把它们写成"通过"，则是自欺——那正是本项目最反对的假象。

## 7. 需要向你追问的情形

遇到以下情况我会**先问再动手**，不猜：

| 情形 | 追问什么 |
|---|---|
| 期望行为不明确 | "正确行为应该是什么？" |
| 触发条件无法从 issue 还原 | "记得当时的操作序列/配置吗？" |
| 症状不可自动断言 | "能接受用 X 作为代理指标吗？" |
| 归类在两可之间 | "这条更贴近 A 类还是 B 类？" |
| 需要真实模型参与（有成本） | "这条要跑真模型吗？还是 mock 就够？" |
| 涉及敏感路径（密钥、外部账号） | "要脱敏到什么程度？" |

## 8. 批量 issue 的处理顺序

一批 issue 进来时，按此顺序处理，**先易后难、先聚类后散点**：

1. **按 kind 分组** —— 同 kind 的 issue 一起处理，driver 改动一次到位
2. **先做已有 driver 能覆盖的** —— 快速形成第一批绿色回归
3. **再做需要扩参数的** —— 扩一个参数通常能覆盖多条
4. **最后做需要新 kind 的** —— 评估投入，必要时分到下一批
5. **说不清的先挂 agent 黑盒** —— 不阻塞流水线

## 9. 迭代记录

每次迭代在汇报里给出固定格式：

```
## 迭代 <N> · <日期>

输入：<N> 条 issue（列出 ID/链接）
归类：kind 分布（tool×3, llm×1, ...）

新增 case：TK-00xx … TK-00yy
扩展 driver：src/kinds/tool.ts（+rewriteResult 参数）
新增 kind：无

运行结果：通过 X / 失败 Y / 跳过 Z / 阻塞 W
失败与阻塞的原因：（逐条）

能力缺口：（测不了的，以及建议）
下一步：（建议优先处理的 issue 类别）
```

`cases/index.yaml` 与 `runs/` 是这份汇报的证据。
