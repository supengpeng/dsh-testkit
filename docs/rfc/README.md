# RFC（Request for Comments）

> RFC 是**把"有多个合理选项"的决定固定下来**的机制。它不是审批仪式，
> 也不是"重要改动才配走"的荣誉通道——判断标准只有一个：
> **这个决定会不会改变别人写场景/接 CI/装插件的方式？** 会 → 先写 RFC。

---

## 1. 什么时候需要 RFC

**必须**先有 accepted 的 RFC（清单一句话版，完整版见[治理 §4](../GOVERNANCE.md)）：

- 新增 kind（第 13 类），或改变 kind 分类学的依据；
- 改 `cases/*.yaml` 的 **schema 语义**（删/改字段；**新增可选字段不算**）；
- 改**冻结的退出码**、`run.json` 既有字段语义、`exports` 既有路径；
- 改**形态**：包名 / `bin` 名 / client 模块 id / `dsh` 清单结构；
- 新增**运行时依赖**；
- 改**默认闸门或沙箱语义**（安全边界）；
- 引入与外部项目的数据交换通道。

**不需要** RFC：修 bug、加测试与守卫、改文档、加**可选**字段、加一条场景、扩某个 driver 的参数。
拿不准就在 issue 里问一句——对齐 10 分钟，返工一个月。

## 2. 编号与文件

| 项 | 规则 |
|---|---|
| 编号 | 四位零填充，**从 `0001` 开始，永不复用**（作废的号也留着，标 `Withdrawn`） |
| `0000` | **保留给模板**（`0000-template.md`），不是真 RFC |
| 文件名 | `NNNN-<kebab-case-短标题>.md`，例如 `0001-new-kind-network.md` |
| 位置 | 本目录（`docs/rfc/`） |
| 状态 | 写在文件头部的元信息表里（见模板），并同步到 §5 的索引表 |

## 3. 状态机

```
Draft ──▶ Discussion ──▶ Accepted ──▶ Implemented
   │            │            │
   │            ├──▶ Rejected
   └────────────┴──▶ Withdrawn
                        │
        Accepted ───────┴──▶ Superseded（被新的 RFC 取代，写清被谁取代）
```

| 状态 | 含义 | 谁能改到这一状态 |
|---|---|---|
| `Draft` | 正文已写完，等讨论 | 作者（提 PR 合并即 Draft） |
| `Discussion` | 已在 issue/PR 里公开讨论，有明确待决问题 | 作者 |
| `Accepted` | **决定**已定，可以据此写实现计划 | 维护者（必须写明裁决理由） |
| `Rejected` | 不采纳 | 维护者（**必须写理由**，并考虑记进 ROADMAP 的「明确不做」） |
| `Withdrawn` | 作者主动撤回 | 作者 |
| `Implemented` | 已落地，指向实现 PR / 版本 | 维护者 |
| `Superseded` | 被某个新 RFC 取代 | 维护者 |

> **`Accepted` ≠ 立刻做。** 它只表示"方向定了"；排期看[迭代计划](../ROADMAP.md)。
> 反过来也成立：没排期不代表方向没定。

## 4. 流程

1. **先开 issue**（或复用现有 issue）：用一段话说清"要解决什么问题、为什么现在解决不了"。
   如果连问题都描述不清，写 RFC 只会把不清楚放大成十页。
2. **抄模板**：`cp docs/rfc/0000-template.md docs/rfc/NNNN-<短标题>.md`（编号取当前最大号 +1）。
3. **填完正文**：背景 / 问题 / 方案 / 替代方案 / 影响 / 验收 / **停止线**。
   「替代方案」必须写**至少一个真的考虑过的**选项，并说明为什么没选——没有替代方案的 RFC 不是 RFC。
4. **提 PR**，标签 `rfc`。合并后状态为 `Draft`（合并即公开，讨论在 PR 里继续）。
5. **裁决**：维护者给 `Accepted` / `Rejected` 之一，并写明理由；同时更新本文件 §5 的索引。
6. **落地**：Accepted 的 RFC 进入 ROADMAP（新 Phase 或并入现有 Phase）；
   实现完成后把状态改为 `Implemented` 并补上版本号。

## 6. 写 RFC 的纪律

- **只写决定，不写实现细节**。实现属于 PR；RFC 里出现大段代码通常说明该拆成两件事。
- **一页能说完就写一页**。篇幅不是严肃性的证明。
- **停止线必须写**：什么情况下**放弃**这个方向（例如"如果实测加速比 < 1.5× 就搁置"）。
  没有停止线的方案会无限期占用注意力。
- **影响面要具体到文件/命令**：改哪些文件、动哪些对外可见的名字、要不要更新
  [迁移指南](../MIGRATION.md)。
- **不要在这里复制 CHANGELOG / ROADMAP 的正文**：引用过去。复制必然漂移。
