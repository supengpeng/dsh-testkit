### 1.2 这份 RFC 的来历（必须先说清）

本 RFC 由一份外部草稿（下称"原稿"，2089 行 v1.3）改写而来。原稿的技术主张被保留，但它有**三类前提错误**——不纠正，任何据此写出的实现都会跑偏：

| # | 原稿的说法 | 事实 |
|---|---|---|
| 1 | §1.1「现状」= DSH 插件发布门槛、强制 Node 22+ 与 Docker、只接受精确几个 DSH 版本、`init` 冲突全量停止、退出码固定 `0-5` | 这是 npm 上 **`iiwish/dsh-testkit` 0.4.4** 的特征，**不是本仓**。本仓是"issue → 场景资产"的平台，无 Docker，退出码 `0-3`，没有 `init` 子命令 |
| 2 | §3「完全重构」= 提取旧行为 → 对拍 → 删旧代码 | 流程本身成立，但对第三方包无从执行（源码不在本仓）；对本仓，原稿连"旧行为是什么"都没写对，§3 的输入是空的 |
| 3 | §4.2 用 `98.8%` / `50%` / `50μs` / `150μs` 论证语言选型 | 全部无出处。本 RFC 一律改为**可复跑的读数**，或**已给出解决方案的待决项**（§8） |

原稿的信息处置（保证不丢）：技术主张 → 本 RFC；接口与协议设计 → [REWRITE-DESIGN.md](../REWRITE-DESIGN.md)；量化标准 → [REWRITE-METRICS.md](../REWRITE-METRICS.md)。原稿第 16 章（总结）与第 17 章（19 条缺点）去重后并入本 RFC §4 与 §7。

## 2. 问题

**当前实现无法回答"一段行为在两个版本之间是否等价"，因为它的比较能力被三个耦合点锁死：**

1. **判定能力与判定对象同语言、同运行时。** 断言引擎、选择器、报告聚合都在 `src/`，即与被测对象（Node/TS 插件与宿主）使用同一门语言、同一个运行时。当被测对象本身出问题时，"工具坏了"与"被测对象坏了"会呈现出同一种失败形态。
2. **没有"旧实现"这个对照物。** 场景是**累积**的回归资产（每条可溯源到一个 issue），它们证明"这个症状不复现"，但不证明"这一版与上一版行为一致"。既有的 `--changed` / `--since` / `--affected-by` 只回答"改了哪些该跑哪些"，不回答"跑出来的结果和以前是否相同"。
3. **组合空间靠人手写。** "多插件共存"与"跨 kind 组合"目前靠 `setup` 里可放多个 kind、`act` 按动作形状分派来手工表达。没有参数化组合入口，组合覆盖就无法度量——[GOVERNANCE.md](../GOVERNANCE.md) §8 的 GFI 与覆盖矩阵只能看到"某 kind 有没有场景"，看不到"组合到第几层"。

### 2.1 不解决会怎样

| 受影响方 | 后果 |
|---|---|
| 维护者 | 任何重构都无法给出"行为等价"的证据，只能靠判断；[MIGRATION.md](../MIGRATION.md) 能写"变了什么"，写不出"哪里等价、哪里不等价" |
| 贡献者 | 新增 kind 要同时懂场景 YAML、driver 契约、fixture 释放纪律；门槛在 [CONTRIBUTING.md](../../CONTRIBUTING.md) §4.1 已被抬高到"先证明确实落不进现有 12 类" |
| CI 消费者 | `run.json` 只回答"这条过没过"，不回答"这条结论有多可信"。模拟宿主下通过的结果与真实宿主下通过的结果，在报告里**不可区分** |

### 2.2 问题的可判定表述

> 给定**同一份场景**与**同一份输入**，当前工具**不能**输出一份"新旧两次执行的逐字段差异报告"，也**不能**为每条结论标注可信度等级。

本 RFC 解决的就是这个可判定的问题。它不含"不够优雅""不够灵活"这类无法验收的表述。

## 3. 方案

### 3.1 决定清单

| # | 决定 | 一句话理由 |
|---|---|---|
| 1 | **语言**：Rust 承担判定、调度、能力门控、对拍；TypeScript 承担场景 DSL、编译前端、报告展示 | 保留"用 TS 写场景"的低门槛，同时把**判定**移出被测对象的语言与运行时 |
| 2 | **形态**：仍是**一个 npm 包**（`src/` 保留 TS，新增 `crates/` 放 Rust，Rust 产物与 `lib/` 一起进 `files`）。**不**改成 npm workspace 多包 | 包名、`bin` 名、client 模块 id 全部不变，把形态类改动压到最小（C6 的活宿主验证只覆盖 `dsh` 清单与 client 半） |
| 3 | **退出码**：`0-3` 语义**逐字不变**，新增 `6/7/8` 表达新语义；`4/5` 保留不使用 | 既有 CI 脚本零改动；新语义不复用旧号，也不撞同名包 |
| 4 | **重构方式**：完全重构（阶段 0 提取 → 阶段 1 新实现 → 阶段 2 对拍 → 阶段 3 删旧），每个阶段带**退出条件与停止线** | 完全重构必须可被叫停，否则它只是无限期占用注意力 |
| 5 | **组合**：引入 `seq / parallel / when / retry / matrix / setup / dependsOn` 与 BaseTool 概念；**推翻 D4**，并改写 [ROADMAP.md](../ROADMAP.md) 的「明确不做」条目 | 组合覆盖必须可度量；在 `setup` 里手工堆 kind 表达不了 3-wise |
| 6 | **分层与可信度**：L0–L6 七层，每条结论标注 `Real / Simulated / Degraded / Static` | 把"这条结论有多可信"变成报告字段，而不是读者的假设 |
| 7 | **协议**：`stdio` + JSON-RPC 2.0，NDJSON 帧；握手纳入消息集；`submit` 只返回句柄，结果经通知或 `wait` 获取 | 闭合原稿的协议漏洞（见 [REWRITE-DESIGN.md](../REWRITE-DESIGN.md) §4） |
| 8 | **防篡改**：JCS（RFC 8785）规范化 → SHA-256 → Ed25519 签名 → 哈希链；链头做**本地锚定**（外部锚定只留接口，设计见 [REWRITE-DESIGN.md](../REWRITE-DESIGN.md) §7.6） | 让报告可被独立验证；**离线可测**的锚定才进本期范围（§8 Q2 已裁决） |
| 9 | **能力门控**：`probe → gate → decision`，决策四态 `Proceed / Skip / Fail / Degrade`；严格档下缺能力只能 skip 或 fail，**禁止 mock 冒充** | 把"如实告知"从口头纪律变成可断言的类型 |
| 10 | **输入源扩展**：除 issue 外接入**测试集**（可复跑脚本 + 原始输出留档）与**数据集**（`.jsonl` / 基准 + 判据），并定义受闸门约束的**自迭代闭环**（自动出提案，**不自动落地**） | 工作区里已有 **246 个可复跑测试资产 / 约 9.3 MB** 与 **88 条边界清单**，它们的寿命不该等于一次会话。"组合出整个工作区的场景"只有这一个入口（§3.4） |

### 3.2 兼容性

| 问题 | 回答 |
|---|---|
| 是否破坏向后兼容 | **是**。`cases/*.yaml` 仍可读，但执行引擎、内部分层与报告字段被替换 |
| `cases/*.yaml` 的 `schema` 要不要升版 | **不需要**（`schema: 1` 保持）。场景**数据结构**不变，改变的只是"谁来执行它" |
| 是否需要 [MIGRATION.md](../MIGRATION.md) 条目 | **需要**。至少覆盖：Rust 工具链前置、退出码新增、`run.json` 新增字段、新子命令 |
| 是否需要活宿主验证（形态类改动） | **需要**（C6）。覆盖 `dsh` 清单与 client 半在真实 profile 下的装载 |
| `source` 结构的放宽 | **需要**：可溯源红线由"`source.issue` 非空"放宽为"`source.issue` **或** `source.ref` 至少一个非空"（suite / dataset 派生者没有 issue URL）；`kind` 缺省 `'issue'`，既有 39 条场景零改动 |

### 3.3 退出码映射表（决定 3 的展开）

| 码 | 语义 | 与 `0-3` 的关系 | 既有 CI 脚本影响 |
|---|---|---|---|
| `0` | 全部 passed / skipped | **逐字不变**（含"选中 0 条归 2"） | 无 |
| `1` | 有 failed / errored | **逐字不变** | 无 |
| `2` | 用法错误，或选中 0 条 | **逐字不变** | 无 |
| `3` | 基础设施错误 | **逐字不变** | 无 |
| `4` | （保留，不用） | 与 `iiwish/dsh-testkit` 的 `4 = unsupported` 区分开 | 无 |
| `5` | （保留，不用） | 与 `iiwish/dsh-testkit` 的 `5 = flaky` 区分开；本仓 flaky 走 `failureCategory: 'flaky'` 进报告，**不改退出码** | 无 |
| `6` | 协议错误（Rust 与 TS 版本不匹配、握手失败） | 新增 | 需新增分支才需处理 |
| `7` | 能力门控失败（严格档下的 `Fail` 决策） | 新增 | 同上 |
| `8` | 层级不允许（严格档下 `Simulated` 结果进入发布门槛判定） | 新增 | 同上 |

> **为什么 `4/5` 保留但不使用**：它们已是同名第三方包的发布语义。**同名不同义是最贵的坑**——当 CI 只能依赖退出码时，一个数字的歧义会跨项目传播。

### 3.4 输入源扩展与自迭代闭环（决定 10 的展开）

**三类输入源**汇入同一条提炼管线：

| 源 | 载体 | 提炼出什么 |
|---|---|---|
| issue | 文本 / 链接 / 会话导出 | 今天的 S1–S5 不变 |
| 测试集（suite） | 可复跑脚本 + 其原始输出留档 | `act` ← 脚本调用；`expect` ← 输出断言 |
| 数据集（dataset） | `.jsonl` / 基准 + 判据 | `matrix` 参数化场景 + 度量断言 |

**四步闭环**，每一步的读写边界都是硬约束：

| 步 | 做什么 | 能写 | 绝不能写 |
|---|---|---|---|
| `collect` | 扫描资产目录 → 资产清单 | **什么都不写**（纯只读） | 任何文件 |
| `extract` | 清单 → 提案（走既有 `testkit_propose`） | `pipeline/proposals/` | `cases/` |
| `refine` | 对 `cases/` 与提案做去重 / 合并 / 补断言 → 精炼提案 | `pipeline/proposals/` | `cases/` |
| `iterate` | 运行结果 + 覆盖缺口 → 下一批候选范围 | **什么都不写**（纯只读） | 任何文件 |

⚠️ **D10 / D11 / D12 一条都不动。** **"自迭代" = 自动生成提案 + 自动准备下一圈的入口，不等于自动落地。** 环上每一圈的进入都必须是人一次 `/testkit issue open`：

```text
人 open（范围 = 某资产目录） → collect → extract → 预检 → 人 approve/reject
   → cases/（draft）→ run → refine → iterate（覆盖缺口）→【回到人 open】
```

工具的责任是把"下一圈该看什么"准备到**只需一次点击**，而不是替人点击。

**覆盖度可计算**：用 `docs/测试场景全景分类.md` 的 **88 条边界清单（EC-01 ~ EC-88）**作覆盖维度，场景标 `covers: [...]`；**覆盖缺口 = 88 − 已覆盖**——它本身就是 `iterate` 的输出，也就是下一批的候选范围。

**schema 冲突必须先解决**：既有红线是 `source.issue` 非空（阻断级），而 suite / dataset 派生的场景没有 issue URL。红线的实质是"可溯源"，故判据改为 `source.issue` **或** `source.ref` 至少一个非空；`kind` 缺省 `'issue'`，既有 39 条场景零改动。完整字段形态与分阶段目标见 [REWRITE-DESIGN.md](../REWRITE-DESIGN.md) §10，指标见 [REWRITE-METRICS.md](../REWRITE-METRICS.md) §14。

## 4. 替代方案

[rfc/README.md](README.md) §6 的硬要求。四个方案都真的评估过：

| 方案 | 优点 | 为什么不选 |
|---|---|---|
| **A. 什么都不做** | 零成本；705 项测试与 6/6 CI 原样保持 | §2.2 的问题持续存在：没有等价性判定、没有可信度字段、组合覆盖不可度量 |
| **B. 保持全 TypeScript，只补缺失能力**（在 `src/` 内加对拍模块 + 可信度字段 + 参数化组合） | 不新增语言与工具链；不动 D1/D4；**705 项测试、65 条契约、13 篇文档全部可复用**；风险最低 | 判定仍留在**被测对象的语言与运行时**内（§2 问题 1 未解决）。且"对拍"要求同时运行新旧两套实现——同门语言写两套，同类缺陷会被同一种写法重复带入 |
| **C. Rust 核心 + TS DSL（本提案）** | 判定移出被测语言；`Send + Sync` 与无数据竞争是编译期保证；`ts-rs` 从 Rust 生成 TS 类型，跨语言契约不手写、不漂移；Rust 侧成熟工具直接可用 | 双语言栈的长期成本（§5）；Rust 编译时间拖慢迭代；团队需同时具备两门语言能力 |
| **D. TS 为核 + Rust 只做热点**（并发调度/隔离换成 Rust 组件，判定仍在 TS） | 增量迁移，无"完全重构"的资产作废 | 判定问题（§2 问题 1）仍未解决，却要付一部分双栈成本——**两头都最差** |

**选择 C 的理由**：本 RFC 的核心问题是"判定必须独立于被测对象"。A/B/D 都没有移动判定的位置，只有 C 移动了。代价在 §5 里被如实计价。

> **原稿缺点 18「Rust 生态的测试工具链不如 JS 成熟」不成立**，事实是反的：快照有 `insta`（crates.io 下载 1.09 亿）、属性测试有 `proptest`（2.06 亿）、基准有 `criterion`（3.03 亿）、覆盖率有 `cargo-llvm-cov`（829 万）、并发排列有 `loom`（7070 万）。原稿当作"生态强"证据推荐的 `cargo-rigtest`，实际只有 **394 次下载**。

## 5. 影响面

| 面 | 影响 |
|---|---|
| **要改的文件** | 新增 `crates/`（Rust）；`src/` 收缩为 DSL、编译前端、报告展示；`lib/` 增加 Rust 产物；`package.json` 的 `files` / `scripts` / `engines` 更新；新增 [REWRITE-DESIGN.md](../REWRITE-DESIGN.md) 与 [REWRITE-METRICS.md](../REWRITE-METRICS.md) |
| **对外可见的名字** | 包名 `@supengpeng/dsh-testkit`、`bin` 名 `dsh-testkit`、client 模块 id、`dsh` 清单**均不变**。新增**两个**子命令（`collect` / `refine`，见下行"CLI 子命令 16 → 18"）；`run.json` **只新增**字段，不删既有字段 |
| **注册面数量** | kind 仍为 **12**（不新增第 13 类）；HTTP 路由数不变；**工具 13 → 15**（+`testkit_collect` / `testkit_refine`）；**CLI 子命令 16 → 18**（+`collect` / `refine`） |

## 8. 待决事项及其解决方案

> 本节**不是问题清单，而是方案清单**：每一条原未决项都已给出可执行的技术方案，并标明它落到哪个设计节。
> 三条解法纪律贯穿全节：
>
> 1. **能靠结构消除的，不靠实测** —— 实测值依赖机器与环境，不可移植；结构约束可移植且可断言。
> 2. **能前移的，不后移** —— 能在 `validate` 期判定的，不拖到运行期。
> 3. **门槛必须机器可判** —— 凡是需要"跑一次看看"的门槛，先问能不能用一个**可计数的结构量**替代它。

### 8.1 决议总览

### 8.2 Q1：并发与确定性

**问题的实质**：不是"能不能同时做到"，而是**把并发放在了哪一层**。原方案让"多线程异步运行时"与"判定"共处一层，那当然要靠实测祈祷。

**方案：并发只用于 I/O，判定路径单线程**

| 层 | 策略 |
|---|---|
| I/O（网络 / 文件 / 子进程） | 允许真并发（多线程异步运行时），因为它只影响"多久拿到结果"，不影响"看到什么顺序" |
| **判定路径**（事件进入断言、调度决策、报告写入） | **单线程 + 显式事件队列**；出队顺序由「种子 + 显式优先级」决定，**不由线程池抢占决定** |
| 用例之间 | **多进程并行**（每用例一个进程），并行度不影响任何单条用例的内部顺序 |

**三条使能措施**：

1. **事件序列可重放**：所有进入判定路径的事件带 `seq`，运行记录保留完整序列；重放时按记录的 `seq` 注入。
2. **C1 的判据升级**：从"结果相同"改为"**事件序列哈希相同**"。更强的同时**更好定位**——不一致时能直接报"第一个 `seq` 分叉的位置"，而不是只报"两条断言结果不同"。
3. **不可确定者必须移出判定路径**：任何无法确定化的输入（OS 级 I/O 完成顺序等）**只允许影响那些已标记为"不参与判定"的字段**。这是**约束**，不是期望。

**验证方式**：`loom` 用来验证**调度器本身**（枚举线程交错，证明队列的出队顺序与线程时序无关），而不是验证整个系统——后者是穷举不完的。

> **结论**：相容。且这个结论不依赖任何实测数字——它是架构约束的推论。实测只用来**验证调度器实现符合约束**。

### 8.3 Q4：签名开销——不是调门槛，是改设计

**问题的实质**：门槛值是机器相关的，写死违背"门槛必须机器可判"；写"待实测"又让指标悬空。

**方案：批量 Merkle 签名**

```text
N 条结果记录 → 构 Merkle 树 → 只签根（1 次 Ed25519）+ 每叶附 inclusion proof
签名次数：O(N/B)   （B = 批大小，默认 4096）
验证成本：O(log N) 每叶
```

**它带来三个后果**：

1. **开销与消息数解耦**：数万条消息按 B=4096 只产生个位数签名 → 签名从"热门瓶颈"变成"可忽略项"。**于是"占比 ≤ 5%"这个门槛本身不再必要。**
2. **指标可机器判定**：D4 拆成两条——
   - **D4a 签名次数上界**：`签名次数 ≤ ceil(结果记录数 / B) + 2`（计数器比对，**与机器速度无关**）
   - **D4b 单次签名耗时**：降级为**基线观测值**（与 D1–D3 同一套冻结基线机制），环境指纹不匹配时只记录不阻断
3. **`criterion` 实测从"门槛来源"降级为"基线采集"**：实测仍需做，但它不再决定门槛。

> **这条是三条解法纪律里第 3 条的范例**：一个需要"跑一次看看"的门槛，被换成了一个可计数的结构量。

### 8.4 Q6：上下文约束取代逃生舱

原方案担心 `compaction.now` 这类动作"只在特定上下文可用"，于是要开"BaseTool 之外的逃生舱"——而逃生舱会让组合器的子图剪枝失去可靠性。

**方案：把"可用上下文"变成 BaseTool 的一等声明**

```rust
pub trait BaseTool: Send + Sync {
    fn kind(&self) -> ToolKind;
    /// 该工具在什么上下文中可用。缺省 = 任何上下文。
    /// 这是**声明**，不是运行期探测，所以 validate 能提前判定。
    fn available_in(&self) -> ContextSpec { ContextSpec::Any }
}

pub enum ContextSpec {
    Any,
    /// 需要真实 agent 上下文（例如 compaction 的 `now`：需要 runMaintenance）
    RequiresAgentContext,
    /// 只允许作用于自身创建的隔离会话（例如 compaction 的 region / now）
    IsolatedSessionOnly,
    All(Vec<ContextSpec>),
}
```

**为什么它不破坏剪枝**：约束是**静态可判**的——`validate` 阶段把场景声明的上下文与每个节点的 `available_in` 求交，不满足**在计划期就报错或 skip**（不是跑起来才发现）。于是剪枝的依据仍然是完整的声明式图，不需要"运行期逃生"。

> **结论**：12 个 kind **全部**落进 BaseTool。`compaction` 的五个动作各自带上下文约束（`compaction-now` → `RequiresAgentContext`；`compaction-region` / `compaction-if-needed` → `IsolatedSessionOnly`；`compaction-inspect` / `compaction-dump` → `Any`），由 `validate` 校验。
>
> **2026-10-11 勘误（阶段 0 行为提取发现）**：原表述为"三个动作"，与源码不符。`src/kinds/compaction.ts:249-253` 的 act 分派有**五个**分支（`ifNeeded` / `region` / `now` / `inspect` / `dump`），其中 `runNow`（`:320-342`）要求 `ManualCompactAgentContext.runMaintenance`，正是 `RequiresAgentContext` 的原始动机——设计稿在风险列引用了 `now`，却漏在原子列。按 RFC §5.1「阶段 1 的产出必须覆盖旧实现的全部可观察行为」，补为**第五个原子**，不回退为"不保留"。

### 8.5 Q10 / Q11 / Q12：三条实现级决议

**Q10 JCS 双实现——做成向量驱动**

```text
spec/vectors/jcs/*.json        输入 + 期望规范化字节（十六进制）
       ↓ 两侧都必须通过全部向量
Rust 实现  ‖  TS 实现
       ↓ 跨实现一致性测试
proptest 生成随机 JSON → 两侧规范化字节必须逐字节相同
```

若某侧因成本无法实现，则**降级为单侧 + 只验证哈希**，并在报告里标 `degraded`——**诚实标注，不静默**（这与本仓"绝不假装成功"的纪律一致）。

**Q11 `Inconclusive` 的升级规则**

连续 3 次（同场景、同判据）为 `Inconclusive` → **升级为失败**。理由：偶发的 `Inconclusive` 是非确定性的正常表现；**连续 3 次说明判据本身有缺陷**（例如容差选错、字段本质不确定）。允许它无限期存在，等于允许"测不准"充当永久挡箭牌。

**Q12 状态快照频率**

默认**每小类前后各一次**（不是只在跨小类边界）：小类内部同样可能污染，而快照成本 = 一次取证 diff，远低于"污染后定位到哪一步"的成本。**降级条件**：若快照开销超过该用例耗时的 20%（由 D1 类基准测得），降为"仅跨小类边界"，并在报告里标 `snapshot: boundary-only`。
